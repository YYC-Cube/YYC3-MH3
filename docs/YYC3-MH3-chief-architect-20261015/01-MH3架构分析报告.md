# 🏛️ YYC3-MH3 全仓架构分析报告

> **角色视角**：首席架构师 × 本地优先全栈工程师 × 可观测性专家
> **分析对象**：`YYC3-MH3`（本仓，React 19 前端生产线工作台）+ `YYC3-MiniMax-H3`（真实引擎 monorepo，对照基准）
> **方法**：全量目录扫描 + 关键文件精读 + git 历史取证 + 交叉 grep 验证，全部结论附文件证据

## 一、执行摘要

| 仓库名 | 一句话定性 | 成熟度 |
| --- | --- | --- |
| **YYC3-MH3** | 工程骨架极佳、**演示语义**的数字人生产线工作台——「本地 Python 推理引擎」只存在于 UI 文案中，代码层零对接 | 骨架 ★★★★★ / 语义 ★★☆☆☆ |
| **YYC3-MiniMax-H3** | 真实运转的 MiniMax-H3 本地生产线：Python 引擎五步闭环 + Vite6/Hono BFF + agent 网关 + manifest 双端契约 | 生产 ★★★★☆ / 卫生 ★★★☆☆ |

**核心判定**：两仓是同一产品的「展示壳」与「发动机」，但**目前零衔接、零互链、职责未划清**——
本仓 `src/`、`server/`、工程文档中 grep `apps/console` / `pipeline_auto` / `3030` **零命中**；monorepo 侧 grep `YYC3-MH3` / `mh3.yyc3.top` 亦零命中。更关键的是：**本仓的五阶段领域模型与 monorepo 真实五步流水线语义上 1:1 同构**（详见 §五映射表），衔接是「认亲」而非「重造」。

## 二、YYC3-MH3 仓库画像

### 2.1 定位与形态

- `package.json:2` 自述「YYC³ MiniMax-H3 DiffSynth 本地数字人生产线 · 五步闭环流水线 · 8 位 AI Family 多智能体协同 · 本地优先 100% 数据主权」
- 技术栈：React 19 + Vite 8 + Tailwind 4 + TS 顶格严格（`strict + noUncheckedIndexedAccess` 等），pnpm 12，oxfmt 格式门禁
- 部署：GitHub Pages 双基座（`BASE_PATH` 动态解析 + CNAME `mh3.yyc3.top`），PWA（手写 SW，`public/sw.js`）
- git 仅 11 个提交（全部 2026-10-15 一天完成基线），属**新建仓**

### 2.2 架构分层（亮点，真落地）

六边形架构（端口-适配器），且有测试护栏锁死：

```
types（全局类型） ← domains（纯函数 + 出站端口 ports.ts）
                      ↑ 被适配器实现：adapters/memory（快照）/ adapters/local（fetch Registry API）
                            ↑ app/composition.ts —— 全库唯一 DI 组合根
                                 ↑ views / components（14 视图 lazy 分包，30 组件）
```

- `src/app/composition.ts` 唯一装配点：dev → local 适配器（回环 BFF 供数、失败降级 memory），静态/测试 → memory 快照
- `src/__tests__/boundary-guard.test.ts` 用 import 方向矩阵固化分层；`offline-guard.test.ts` 静态扫描全库，公网 http(s) 字面量一律 fail——**零公网红线是测试守卫，不是口头承诺**
- `server/registryApi.ts`：框架无关纯函数 BFF（八端点，契约见 `docs/06-Registry-API-契约.md`），由 `vite.config.ts` 挂进 dev server `/api/*`，`apply: "serve"` 不进产物；回环 Host 校验 403
- 韧性网关 `src/adapters/local/http.ts`：双保险超时 + 404 业务空值 + 降级/恢复状态机留痕

**架构师结论**：换真实后端时前端只需换适配器实现——**这座桥的桥墩已经打好**。

### 2.3 工程质量门禁（CI 28s 级）

`ci.yml` 四连：`oxfmt --check` → `tsc --noEmit` → `vitest run`（11 文件 110 用例）→ 双基座构建冒烟；`deploy.yml` Pages 自动部署。全库 `any` 仅 2 处（`vite.config.ts` ws.send 包装）、TODO/FIXME 0 处、每文件 YAML 标头。

### 2.4 本地优先落地评估（本地优先工程师视角）

| 维度 | 现状 | 判定 |
| --- | --- | --- |
| 不出网 | offline-guard 测试门禁 + @fontsource 自托管字体，SW 预缓存仅 manifest/favicon | ✅ **真红线** |
| 可拥有 | **零持久化**：全库无 localStorage/IndexedDB 调用，种子库/批次/配置刷新即失 | ❌ 缺失 |
| 诚实的 UI | `OpsMonitorView.tsx:414`「日志保留在本地 IndexedDB 与 WAL 磁盘目录」、`SettingsView.tsx:77`「配置已持久化至本地 IndexedDB」——**均为纯文案，无实现** | ❌ **虚假陈述（P0）** |
| 可迁移 | 无导出/导入种子库能力（Settings 仅 toast） | ❌ 缺失 |

**结论**：「100% 数据主权」目前只兑现了「数据不出网」（必要条件），未兑现「数据可拥有/可迁移」（充分条件）。

### 2.5 可观测性评估（可观测性专家视角）

现状空心：全库 `console.*` 0 处、无 ErrorBoundary、无 `window.onerror`/`unhandledrejection` 监听、无任何前端留痕 sink——生产 SW 场景下错误**静默消失**。仅有的真实可观测件：
- BFF 降级/恢复留痕（内存日志表 → TerminalLogPanel 可见）
- `GET /api/health` 真实 uptime
- `TerminalLogPanel` 页脚「SSE 长连接 / CUDA:0 RTX 4090」为**装饰性假状态**

其余（指标/告警/日志面板）全部为 `src/data/ops.ts` 快照，例如 `ops.ts:147`「DiffSynth 推理引擎 (CUDA:0) 端口 9100」是 mock——**而真实引擎跑在 Apple M4 Max MPS，根本没有 CUDA**，文案与事实双重脱节。

### 2.6 缺陷与债务清单（分级）

| 级 | 编号 | 问题 | 证据 |
| --- | --- | --- | --- |
| P0 | D-1 | 「本地推理引擎」衔接完全缺失：无进程管理/健康探测/GPU 采集/任务下发/进度回传/SSE | 预研自认 `docs/YYC3-MH3-impl-expert-20261011/04-Registry真实采集可行性预研.md:63` |
| P0 | D-2 | UI 谎称已持久化（IndexedDB/WAL）与假运行态（SSE/CUDA） | §2.4/§2.5 所列 |
| P1 | D-3 | 零持久化 + 零导入导出，种子资产不可拥有 | `adapters/memory/*` 闭包变量 |
| P1 | D-4 | 前端可观测性零基建（错误上报/性能/日志 sink） | §2.5 |
| P1 | D-5 | 模拟流水线 `setInterval` +5%/s、AI Family canned 回复均为演示道具 | `WorkbenchView.tsx:210-232`、`YYC3FamilyModal.tsx:218` |
| P2 | D-6 | 状态全靠 props 下钻（无状态库），14 视图规模化会劣化；`useProductionData` 每渲染建孤儿适配器实例 | `App.tsx`、composition 调用点 |
| P2 | D-7 | 仓库卫生：docs 下 830 个未跟踪本地文件（39MB）与工程混居 | `git status` / openclaw ignore 规则 |
| P2 | D-8 | 主包 304KB + CSS 470KB（字体内嵌偏大） | `dist/` 产物 |

## 三、YYC3-MiniMax-H3 仓库画像（对照基准）

### 3.1 定位与形态

真实生产线 monorepo（v1.1.0，355 tracked files）：**Python 引擎**（根 `scripts/`）+ **前端工作台** `apps/console`（Vite 6 + React 19 + Hono BFF 单端口 3030——根 `package.json` description「Next.js 控制台」已过时）+ **共享契约** `packages/manifest-schema`（zod 双端唯一真源，CI 用 `git diff --exit-code` 锁 JSON Schema 漂移）。

### 3.2 引擎能力边界（输入 → 输出）

- **输入**：`ref_images/`（已结构化 characters/scenes/props）+ 六段式提示词模板（`prompts/README.md`）+ seed 列表 + 档位（全质量 480×832×124帧×50步 ≈ 3.6h/条；preview 360p×64帧×30步）
- **过程**：五步闭环 `pipeline_auto.py --batch NN --auto [--dry-run]`（断点续跑、SIGTERM 优雅收敛、单飞锁、夜间窗口 22:00-08:00 硬约束）
- **输出**：`output_batchXX/{ref}/h3_seed_{seed}.mp4` + `manifest.json`（单一事实源：params/records/性能计时 gen_seconds·peak_rss_gb·mps_alloc_gb/SyncNet 评分）→ 聚合 `dashboard/data/batches.json`
- **硬约束**：Apple M4 Max MPS 本地推理（**非 CUDA**）、模型缓存 `~/.modelscopes/` 约 72.5GB、权重经 `vendor/DiffSynth-Studio` submodule（modelscope 官方仓）

### 3.3 对外接口三种形态（Web 前端对接面）

1. **CLI**：`pipeline_auto.py`（唯一被 BFF 白名单 spawn 的入口）
2. **HTTP**：console BFF（Hono 3030，14 端点 + SSE `/api/pipeline/stream` 四事件 state/log/file/heartbeat，spawn 管线 + `fs.watch` 文件总线；令牌 fail-closed、未配置回环放行）；agent 网关（FastAPI 8300，三 Agent + 编排器，X-Claim-Token HMAC）
3. **文件契约**：`manifest.json`（zod + JSON Schema 双端锁定，含 `reason` 七值失败枚举与 `reconciled` 块）→ `batches.json` 聚合 → dashboard HTML / console `/api/dashboard` 消费

### 3.4 可观测性现状

有真材实料但未成体系：结构化 JSONL（`watchdog_alerts.jsonl` 指纹去重三级升级、`audit_log.jsonl`、`console_watch.jsonl` P95 采样）+ launchd 看门狗探活 + manifest 内嵌性能计时（**全系统最细粒度观测数据**）。缺：统一 metrics/tracing、运行日志多为非结构化文本。

### 3.5 工程卫生问题

根目录物理堆放 27 个 `output_batch*/` + 29 个 `report_batch*.md` + 15 个 `analysis_result*.md`（gitignore 已覆盖，纯本地噪音）；`models/**.safetensors.incomplete` 下载残留；README 目录树未更新 apps/packages 结构；工作区不干净（README/batches.json 已修改未提交）；`.idea/.mimosa/.v2c/.video_agent` 新工具目录未被 gitignore 覆盖。

## 四、双仓对照矩阵

| 维度 | YYC3-MH3（本仓） | YYC3-MiniMax-H3 | 差距本质 |
| --- | --- | --- | --- |
| 角色 | 展示壳 / 工作台 UI | 发动机 / 引擎 + BFF + 契约 | 未接线的两端 |
| 前端栈 | Vite 8 · 无路由 · 无状态库 · hexagonal | apps/console：Vite 6 · react-router v7 · zustand · Hono BFF | **双前端并存，职责未定** |

| `PIPELINE_STAGE_ORDER[0]` generation | ① `batch_ref2va_nf4` 批量生成 | ✅ 同构 |

| `fine_eval` | ③ `report_batchXX.md` 人工精评 | ✅ 同构 |
| `analysis` | ④ `analyze_report` 双格式分析 | ✅ 同构 |
| `seed_iter` | ⑤ `update_seed_list` 最优 Seed 写回 | ✅ 同构 |
| `SeedItem`（tier S/A/B + 五参数 + history） | manifest record（seed + params + lipsync.score_norm + human.score） | 需字段映射 |
| `BatchItem` / `GET /api/batches` | `batches.json` 批次聚合（status 状态机五态） | 需字段映射 |
| `ServiceStatus` 端口 9100 假服务表 | console 3030 / agent 8300 / 0379-World 网关 | 端口语义待换血 |

**结论**：本仓的领域模型显然是照着真实生产线建的——衔接不是「两个产品集成」，而是「壳认发动机」。五阶段命名、种子概念、批次概念全部对得上，缺的只是数据通道与契约统一。

## 六、总体结论

1. **YYC3-MH3 是一份优秀的「工程骨架」加一层「演示皮肤」**：架构分层、测试门禁、零公网守卫达到产线水准；但核心叙事（本地引擎调度、数据主权、可观测）三者为零落地或虚假落地。
2. **YYC3-MiniMax-H3 是真实生产力**：五步闭环、双端契约、看门狗运维均已实战运转（24 个批次、dry_run 事故已根修、NAS 归档闭环）。
3. **衔接的架构条件已全部具备**：本仓三端口（`SeedRepository`/`BatchRepository`/`TelemetryPort`）+ `createRegistryApi({collector})` 注入口 + monorepo 的 BFF/SSE/文件契约/manifest-schema——**桥墩在两岸都已打好，只差架桥**。具体架桥方案见同会话《02-MiniMax-H3衔接整改报告》。
