## 四、阶段三排期：Registry API 本地 BFF（Phase 8，PR-10 ~ PR-12）

### 4.0 契约遵循声明

> 端点、字段、错误约定、验收清单**逐字以 [06 契约 v1.0.0](../06-Registry-API-契约.md) §2/§3/§6 为准，不新增、不裁剪、不虚构**。任何契约变更先改 06（版本 +1）再改实现。前端禁止硬编码端点（URL 一律 `import.meta.env` 注入）。

### 4.1 形态决策（取证后定稿）

| # | 决策 | 内容 | 取证依据 |
| ---- | ---- | ---- | -------- |
| D1 | BFF 形态 | **Vite dev server 中间件插件**（同源同端口 8443）；BFF 逻辑独立为根级 `server/registryApi.ts`（`handleRequest` 纯函数可测），插件薄壳仅桥接 `/api/*` | vite.config.ts 已有 3 个 `configureServer` 插件先例；零新增 npm 依赖（契约 §1.4 无外部依赖） |
| D2 | 回环控制 | dev server 宿主需 `0.0.0.0`（FIGMA_DEV_SERVER_HOST，Figma Make 宿主约束不可收紧）→ **`/api` 中间件校验 Host 头，仅放行 `127.0.0.1`/`localhost`**（「API 面回环 only」等价实现；§6 验收第 1 项按此口径勾选） | .env.example L17 + 契约 §1.1 |
| D3 | 数据源 | server 侧复用 `src/data/*` 快照为初始态（内存可变：PATCH alarms / POST seeds），进程重启回归快照（演示语义，如实声明） | 契约 §2「对应现行 mock」列 |
| D4 | URL 注入 | `VITE_REGISTRY_BASE_URL`（.env.example L30 预留行激活）+ 缺省由 `VITE_APP_PORT` 构造；代码零硬编码端点 | 契约 §5 + .env.example §Registry API |
| D5 | 降级留痕自举 | local telemetry 的降级/恢复事件写自身 logs 通道（内部持有 memory 实例），闭环 Runbook §3.3 | 契约 §4「降级与恢复事件必须经 TelemetryPort 留痕」 |
| D6 | 装配策略 | dev（`import.meta.env.DEV`）组合根装配 local（内置 per-call 降级）；静态/preview 场景 memory 直连（避免必然失败的请求噪音；契约红线「零公网」不破坏） | 契约 §4 图示 |

### 4.2 PR 分解

#### PR-10: BFF 服务端落地（契约八端点整体交付）✅ 已交付 2026-10-12

**目标**: `GET /health`、`GET /services`、`GET /metrics`、`GET /alarms`、`PATCH /alarms/:id`、`GET /logs`、`GET /batches(+:id)`、`GET /seeds` + `POST /seeds` 全部在线且字段逐一对型

| Task | 内容 | 验收标准 |
| ---- | ---- | -------- |
| 10.1 测试先行 | `server/registryApi.test.ts`：`handleRequest` 八端点用例（响应字段逐一对照 `src/types/index.ts` 断言）+ 404/400 错误约定 `{error:{code,message}}` + Host 非回环 403 | 测试绿后才开始实现 |
| 10.2 BFF 实现 | `server/registryApi.ts`：路由表 + 内存态（data 快照引导）+ 查询参数（`?from=&to=` / `?resolved=` / `?stage=&level=`）+ `PATCH /alarms/:id` 与 `POST /seeds` 可变态 | 字段与 types 逐字段一致；非 2xx 走错误约定 |
| 10.3 插件薄壳 + env | vite.config.ts 追加 registryApi 插件（configureServer 桥接，Host 校验）；.env.example 激活 `VITE_REGISTRY_BASE_URL` | curl 八端点 200；非回环 Host 403 |

**依赖**: 无（PR-9 端口面已就绪）。**风险**: vite.config bundle 引用 TS 依赖的加载时机（R2）——首项验证，异常降级 `ssrLoadModule`。

## 五、阶段四排期：Registry 真实采集（Phase 9，PR-13 ~ PR-14）

### 5.0 预研结论声明

> 可行性预研已完成（2026-10-12），**结论：可行且优于预期**——逐字以 [04-Registry真实采集可行性预研.md](04-Registry真实采集可行性预研.md) 为准（四组实证 + 数据源矩阵 + 混合语义架构）。关键发现：GPU 利用率/显存经 `ioreg IOAccelerator` **免 sudo 可采**。本节排期不新增、不裁剪预研结论。

### 5.1 语义分级（混合模式，04 §四）

| 级别 | 字段 | 语义 |
| ---- | ---- | ---- |
| L1 真实 | cpuUtil / memUtil / gpuUtil / gpuVram / diskIops | 真实采样值直出 |
| L2 演示保底 | temp / 服务表 | 采集失败或探测全 offline 时回退演示快照 |
| L3 不变 | alarms / logs / batches / seeds | 维持 D3 演示 + 留痕语义 |
